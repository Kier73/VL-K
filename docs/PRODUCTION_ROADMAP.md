# Production roadmap — original kernel track

**Update:** this is the original-kernel roadmap from K3.1, retained as a historical research plan. For current conventional product strategy, reviewed against unkernel at K3.2.10, see [conventional substrate](CONVENTIONAL_SUBSTRATE.md). Adopt the full Linux baseline first while retaining original-kernel experiments and qualifying bottom-up substitutions.


Baseline: K3.1, commit 0c1122b4f1d3b5441f8041000d09600d82df3be4. The goal is an independently bootable, general-purpose operating environment with conventional application interfaces, capable of hosting mathematical discovery and interactive learning. Correct conventional execution is the baseline; Virtual Layer optimization is an optional realization method. No application must require a successful Ground discovery to execute. General-purpose means support for arbitrary algorithms within available resources and supported ABI profiles, not every existing architecture or device by default.

## Current boundary

The shared C RV32IM interpreter loads a restricted static ELF32, uses a 4 MiB flat memory and page permissions, and dispatches a small Linux-number syscall subset. RVFS supplies an eight-file flat namespace (256 KiB each), a descriptor table and stdio state. Hosted volumes persist through successful guest exit; bare metal uses volatile RAM files. The hosted and freestanding runners each have one RV instance and one RVFS instance. File storage and descriptor ownership must be separated for real multiprocess behavior. rv_load stages directly into the caller's machine and RAM, so a late load failure is not an atomic executable replacement. Existing pure debugger/authority checkpoints concern a different guest architecture and cannot be treated as RV32 machine snapshots.

Local audit: filesystem suite rerun through dist/vlk run python3 tests/fs.py; 16 native/guest command comparisons, 196 KiB file transform, eight counter restarts, independently parsed persisted bytes, descriptor/seek/append checks and negative volume tests passed. Eleven K3.1 implementation/test/build blob identities matched the local files. Current remote branch audit found only main and zero open PRs. Kernel, independent boot and reciprocal bootstrap CI were queued at this checkpoint. No local QEMU, no verified boot, and no fresh full regression claim.

## Architecture to converge on

- Machine backend: decode, step, bounded run, architectural fault and portable machine-state export.
- Process: logical PID, machine context, address space, per-process descriptor table, credentials/capabilities, lifecycle and scheduler state.
- Kernel objects: shared file objects, open-file descriptions, pipes, terminals, timers, memory objects and network endpoints. Descriptor slots reference objects; shared storage is not a shared descriptor table.
- ABI adapter: architecture-specific register/structure marshalling and Linux-number translation to architecture-neutral kernel operations; never reuse x86-64 numeric layouts for RV32.
- Platform: memory allocation, console, monotonic clock, block and network device adapters. Host POSIX and freestanding hardware implementations remain distinct.
- Observation layer: canonical closed machine/kernel state and explicitly identified external effect boundaries. Evidence, candidate construction, verification and execution are separately accounted. Optimization is disabled by default during compatibility qualification.

## Ordered production milestones

K3.2 — Runtime and loader. Stage and validate executable images before commit. Make address-space capacity configurable within platform resource bounds; implement startup stack/environment/auxv, required ISA features, anonymous memory mapping/protection/unmapping, stat and necessary descriptor operations, errno and pointer fault semantics. Pin a reproducible static libc toolchain and qualify its actual ELF output; record the required ISA/ABI and unsupported calls rather than assuming compatibility. Acceptance: independently authored small libc program and a standard utility, unmodified upstream source, compiled with normal target startup and libc; compare stdout, stderr, status, memory-visible behavior and file effects against a Linux reference. No custom syscall wrappers in acceptance application.

K3.3 — Independent boot and storage (parallel with K3.2). Obtain actual QEMU serial transcript and artifact from boot-test; until then the existing Multiboot image is an unverified boot target. Parse Multiboot memory map, establish allocator/exception handling, timer and interrupts; admit a boot module containing a filesystem/application archive. Launch ELF files from that supplied archive without relinking kernel. Then introduce a block device adapter and persistent volume with crash-consistency tests. Acceptance: boot without a hosted runtime, load external executable, execute multiple launches and verify persisted files after reboot. Boot module transfer alone is not persistent storage.

K3.4 — Processes and interactive shell. Separate storage, open-file descriptions and descriptor tables; add process lifecycle, isolated address spaces, cooperative scheduling before preemption, blocking/wakeup semantics, pipes, dup/close, exec replacement and wait; console line discipline and terminal interaction. Acceptance: two isolated applications with concurrent progress, pipeline and child exit, blocked reader wakeup, bad pointer isolation, repeated launch without leaks and state equivalence under varied quanta.

K3.5 — Real research workloads. First qualify a small upstream static utility, then SQLite with real database file transactions and independent integrity checks (initially an explicitly documented single-process/no-WAL profile if needed), then a small C compiler/interpreter and Python runtime. Use unchanged upstream source, pinned toolchain, explicit build configuration and actual guest execution. The hosted native launcher remains useful for building and testing, but does not count as guest compatibility. If RV32 libc/tooling or memory constraints obstruct the path, qualify RV64 as an additional backend rather than silently redefining the workload or abandoning the shared kernel interface. Dynamic linking, TLS, broader ISA, signals and threads follow measured workload requirements.

K3.6 — E-CPU and adaptive execution. Run original E-CPU runtime inside a qualified language environment, then expose VL-K closed-state/observation operators through receiver-owned E-CPU admission. First demonstrate one complete checkpoint handoff and native-vs-restored successor equality; then authenticated transport, fenced effects and placement across independent hosts. Feed actual workload traces and qualified operation costs to the Ground discovery layer. Admit optimization only against explicit register, memory, logical-time, syscall and effect equivalence. Measure end-to-end gains including discovery, verification and transport; retain conventional fallback.

## Cross-repository reference contracts (read-only review)

- E-CPU at 09a9058a43c139c476609954636e17e7fadcfd37: mailcpu/elf.py and tests/test_elf_runtime_admission.py separate staging, linking, startup and backend admission; mailcpu/posix_abi.py separates architecture-specific ABI marshalling from native kernel transitions (x86-64, not RV32); docs/STREAM_HOSTED_HEADLESS_OS.md describes closed OS-state reconstruction and process-failure cuts; docs/VLI_TEMPORAL_OS_HOSTING.md describes pinned actual runtime admission and successor publication. Treat these as design/test references, not a C-port dependency.
- Virtual-Ground-Interpreter at 39a169b21513ffaaee85e40826c706c07a47215b: virtual_ground_interpreter/vgi/structural_memory.py separates expensive structural search from rechecking a portable witness. Apply to candidate optimization cache only after conventional correctness.
- In-Formation-Space at ccf7dfb88a52c458ee9dd00e26ffbaecf5b2af9c: bridges/observation-path/operation_spans.py defines clock-qualified wall-time measurements, distinct from CPU time; experiments/proof-runner-independent-reconstruction/README.md documents independent authority/runner/verifier roles. Reuse the measurement and evidence separation, not assumptions of distributed consensus.
- VL-64 at 46d58dd3f445de4e1f898e0d9f9c1e41d68b59d2: docs/UNIVERSAL_BYTE_GROUND_AND_EXECUTION.md separates byte identity, typed interpretation, execution and verification. Use for executable/module capability discovery and source identity; a byte representation alone is not an execution backend.
- VL-I at 00fd4026dc3c35bc130d2d09ab9d88b354616d7b: docs/TIME_010_NATIVE_RATIONAL_EXECUTION.md demonstrates source-qualified law execution through E-CPU's real operator runtime, independently compared with a navigation evaluator. Target this kind of real research application and evidence, rather than a new illustrative clone.
- E-CPU-Virtual-Processor at e3a511369756929b518df11f5f7c0ff161d143ce: README.md describes a narrow affine processor with stable identity and replayable request history. Its identity model may inform closed VL-K process observations; it is not a general-purpose VM.

No upstream source was copied, no other repository was modified, and no third-party application execution or independent boot is asserted by this roadmap. Keep ABI compatibility and the independent boot target as the mainline priority until external application workloads are genuinely hosted.

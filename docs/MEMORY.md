# K2.2 — Byte-addressed memory

Memory(size, data=None, pattern=None) supplies exact bytes on demand. A resident backing is immutable and must match size; default backing is zero-filled; a nonempty periodic pattern is an exact coordinate law. The only application-facing operations are byte ranges: read(start,size), write(start,data), fork(), stats(). A modified page is a 4096-byte immutable overlay (short at a partial final page). Restoring the base content removes the overlay. Fork shares immutable backing and overlay payloads and copies the overlay dictionary, O(number of modified pages), not O(logical size). Shared address-space mappings retain the same Memory object instead.

AddressSpace maps nonoverlapping fixed ranges of the unsigned 64-bit address domain, with whole-mapping read-only or writable protection. Adjacent ranges can be read/written in one call. All mapping/permission checks precede a write; this does not guarantee rollback on allocation failure. Zero-length accesses require only a valid coordinate. Unmap and protect take the mapping's exact start. Software-only, serialized owner; not a host memory protection boundary, process VM, MMU or cross-process sharing protocol. Requests materialize returned bytes; callers must bound read sizes. Range lookup is logarithmic in mapping count; insertion/removal shifts the sorted index. A read of an untouched periodic byte uses its offset modulo pattern length; no preceding pages are evaluated. Materialization work scales with requested bytes/pages. Writes reconstruct touched base pages and preserve exact untouched bytes. Stats count backing and overlay payload bytes, excluding Python metadata, transient buffers and allocator overhead; shared payloads may appear in more than one mapping's stats.

## Executed tests

Nine local suites passed through a clean managed self-build. Memory differential: 3000 randomized mixed reads/writes against bytearray and resident backing; cross-page and cross-mapping operations, private forks, shared mappings, protection and gap rejection before mutation, restored-overlay eviction, 1000 distant reads. A 1 TiB periodic logical mapping retained a five-byte pattern and three modified pages (12288 payload bytes) after writes near both ends. Fork divergence preserved original and child bytes. No physical terabyte allocation or arbitrary-memory compression claim. Independent CI is separate.

## Next

Make this address space the memory service of a kernel-managed instruction process, add typed backing admission and bounded reads, then compare against mmap and ordinary bytearrays for realistic dense/sparse workloads. Exact structural backing must be selected only where advantageous; unsupported data retain resident semantics. Source-backed memory requires pinned content identity and explicit availability/failure semantics.

## Adversarial validation and workload evidence

The stress suites use a distinct eager byte oracle (20,000 map/read/write/protect/unmap/fork/audit operations), actual host mmap (20,000 random reads and writes against an 8 MiB buffer plus a complete digest), real SQLite database pages (8,000 rows; reconstruct old/new snapshots and independently run SQLite integrity and aggregate checks), and a test-only budgeted checksum guest (1,572,868 executed instructions, fork with a divergent 4,097-byte patch, independent zlib Adler-32 oracle). The guest is a test fixture, not an executable loader. The state machine admitted 11,225 operations and rejected 8,775 with matching error categories; no discrepancies. The SQLite mutation touched 223/225 pages: dense changes undermine the storage advantage of immutable resident backing plus overlays. The original backing can still be useful for snapshots, but a density-aware rebase policy is worth testing.

Two input defects were found: boolean/float aliasing of mapping keys through unmap/protect/stats and integer writes interpreted as zero-filled lengths. Strict address and buffer-protocol validation now reject these. Direct backing reads avoid page traversal when no overlays exist; single-page reads bypass accumulation. See benchmarks/memory_reads.py for a reproducible read comparison against mmap. A clean self-build passed all 11 suites locally; a prior run exceeded the tool's 25-second timeout, so it was rerun from a clean build with a larger timeout. No evidence of a test deadlock in the successful rerun. Remote CI is independent.

Benchmark: 30,000 64-byte reads from a 16 MiB range, five shuffled repetitions, median mmap 7.43 ms, resident VL-K 14.16 ms, periodic VL-K 19.66 ms. All returned the same digest. Excludes mapping setup, includes loop and hashing. These are local timing observations, not universal ratios.

Research implications: treat the representation, its overlay density, and observation workload jointly as the cost model. Compare to conventional lazy mmap (zero-backed memory is not itself novel), account for setup/verification and avoid claiming that compact storage implies faster access. IFS can use SQLite as an independent authority consumer; VGI can verify exact byte laws with independent observations; E-CPU can test transfer/read cost and snapshot density before choosing a structural backing. These are proposed integrations, not deployed changes in those repositories.
